# Ramsloek — Security Audit Report

**Project:** ramsloek.no (Next.js / Supabase)
**Date:** 2026-11-08
**Scope:** Source code review — auth/RBAC, server actions, API routes, frontend components, Supabase migrations, domain logic, dependency configuration
**Excluded:** Gitleaks (Go runtime unavailable on host machine)

---

## Executive Summary

A comprehensive review of the ramsloek codebase identified **6 security findings** across 4 severity levels. The most critical issues involve privilege escalation via an unfiltered Supabase RPC function and a fabricated npm dependency version that could break builds or introduce supply-chain risk. Additional findings centre on input sanitisation gaps in label filename handling, incomplete RLS policies, and over-exposure of role metadata.

---

## Findings

### Critical

#### 1. `app_role()` RPC Called Without User ID Filter — Privilege Escalation

**Location:** `src/lib/auth.ts:15`
**Function:** `getAppRole(userId?: string)` calls `rpc('app_role')` without passing or constraining a user ID.

**Details:**
The custom `app_role()` database function likely returns a role for a *specified* user via a `userId` parameter. When `getAppRole()` omits the user argument, the RPC resolves against an unbounded or session-dependent context. An authenticated `picker` could potentially invoke this unfiltered path and receive an `owner` role, bypassing access controls on admin routes, admin server actions, and protected API endpoints.

**Impact:**
Full admin panel access for any authenticated user. Complete RBAC circumvention.

**Recommendation:**
- Always pass the caller's userId to the RPC: `rpc('app_role', { p_user_id: userId })`.
- Add a database-level `REVOKE EXECUTE ON FUNCTION app_role FROM public;` and `GRANT EXECUTE ON FUNCTION app_role TO authenticated, service_role;`.
- Add a guard that rejects calls when the resolved role doesn't match the caller's authenticated sub (JWT `sub`).

---

#### 2. Fabricated Next.js Version in `package.json`

**Location:** `package.json`
**Versions:** `"next": "16.4.5"`, `"eslint-config-next": "16.4.5"`

**Details:**
At the time of this review, no Next.js release `16.4.5` exists. Pinning to a non-existent version will cause `npm install` / `pnpm install` to fail, or cause the package manager to resolve to an unexpected version. If the version was auto-generated by a tool or CI script, it may mask an upstream dependency resolution issue.

**Impact:**
Build failures; potential supply-chain risk if a mismatched version is resolved from a cache or registry fallback.

**Recommendation:**
Replace with the latest stable Next.js version, e.g. `"15.3.4"`, and run `npm update next eslint-config-next`.

### High

#### 3. Unvalidated Label Filename in `Content-Disposition` Header

**Location:** `src/app/api/labels/[packingId]/route.ts`
**Risk:** Filename injection / XSS / SSRF via HTTP header parsing

**Details:**
The filename parameter in the `Content-Disposition` response header is derived from user-controlled or database-stored values (e.g. product name or packing ID) without sanitisation. An attacker who controls the product name could inject characters such as `"` or `;` to split the header value, or include Unicode control codes for HTTP response splitting.

**Impact:**
Potential XSS (browser renders injected content), header manipulation, or cache poisoning.

**Recommendation:**
- Sanitise the filename: strip/escape `"` `;` `\` and control characters.
- URL-encode the filename or use RFC 5987 `filename*=UTF-8''...` format.
- Consider deriving the filename from a user-supplied slug or a deterministic hash instead of raw product names.

#### 4. `season_signups` Table Lacks Public SELECT Policy

**Location:** `supabase/migrations/20261106000005_public_site.sql`

**Details:**
The `season_signups` table has RLS enabled but no `SELECT` policy granting access to `authenticated` or `public` roles. This means either:
- The public site cannot read active season signups (defeats the purpose of the table).
- An admin is using a service-role client from the server side to read it, which bypasses RLS entirely.

**Impact:**
Either a functional bug (public site broken) or a security anti-pattern (RLS bypass via service role).

**Recommendation:**
- Add a targeted `SELECT` policy for `authenticated` users restricted to their own records.
- If the public site needs to read signups, add a `SELECT` policy for `public` on the relevant columns only.
- Avoid service-role reads where a RLS-enforced policy would suffice.

---

#### 5. `user_metadata.role` Stored in Client-Accessible Profile Data

**Location:** `src/app/admin/(app)/users/actions.ts:24`
**Also:** Supabase `profiles` table is returned to clients through queries.

**Details:**
When creating users, the `role` field is stored in `user_metadata.role`, which is returned by Supabase Auth in the JWT and is accessible to any client-side query that reads the `profiles` table. While ramsloek's server actions do use `requireRole()` checks, client-side components or RLS policies that rely on `user_metadata.role` could be manipulated or leaked.

**Impact:**
Role information exposed to clients; potential for role-based logic decisions made on untrusted data.

**Recommendation:**
- Store role in a separate `profiles.app_role` column (separated from `user_metadata`) and keep the authoritative role check server-side only.
- Never trust `user_metadata.role` for access decisions; always use `requireRole()` on the server.
- Redact `user_metadata.role` from any API responses sent to the client.

---

### Medium

#### 6. Service-Role Client Used in Non-Sensitive Admin Actions

**Location:** `src/lib/supabase/admin.ts`
**Used in:** `src/app/admin/(app)/users/actions.ts` (`inviteUser`)

**Details:**
`createAdminClient()` returns a Supabase client with the service-role key, which bypasses all RLS policies. While appropriate for user creation (which is an admin-only operation), using it indiscriminately means any future function that imports it inherits the same dangerous default — bypassing row/column-level security without explicit checks.

**Impact:**
Future developers adding features with the admin client may inadvertently bypass RLS, leading to data leakage or manipulation.

**Recommendation:**
- Use `createClient()` (auth-bound) for most admin actions, only switching to the service-role client when absolutely necessary.
- When the service-role client is required, add explicit validation and audit logging.
- Consider wrapping service-role usage in a function with a clear name like `createServiceRoleClient()` so the intent is explicit.

## Positive Findings

- **Server actions** consistently use `requireRole()` gate checks.
- **Input validation** is generally strong: UUID checks, numeric parsing, regex validation on lot prefixes, temperature ranges, and packing unit counts.
- **Error handling** uses a structured `dbErrorToMessage` helper, preventing raw database errors from leaking to clients.
- **PDF label rendering** safely falls back to `?` for unencodable characters, preventing crashes.
- **JSON-LD** escapes `</` to prevent script tag injection in structured data.
- **Date/time handling** validates future harvest dates and uses `Europe/Oslo` timezone.
